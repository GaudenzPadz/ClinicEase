Manual appointments are hard to manage.

Small clinics still rely on calls, visits, and informal records. Five problems follow from that.

04 / 09
Workflow

How ClinicEase Works

A straightforward three-step workflow designed for patients and healthcare providers.

1
calendar_month

Choose a slot

The patient logs in and sees only slots marked Available. Staff create these slots; patients cannot invent times.

2
event_available

Submit and confirm

The patient fills in contact details and purpose, then answers "Save this appointment?". The system re-checks the slot right before saving.

3
notifications_active

Staff review

The request is saved as Pending. Staff confirm or cancel it, and the patient is notified in the app and by email.

05 / 09
Statuses

Appointment Status Lifecycle

Clear visual indicators keep all parties informed at every stage.

Pending

Request saved. Waiting for staff review. The slot is Booked.

east
Confirmed

Staff approved the request.

east
Completed

The appointment took place. Only a Confirmed appointment can reach this.

southPending can also move here Cancelled

Staff cancelled. The slot becomes Available again.

Allowed changes: Pending → Confirmed, Pending → Cancelled, Confirmed → Completed. Any other change is rejected by the system.

06 / 09
Business Rules

Fair, first come, first served.

The backend protects every slot, even when two patients click at the same moment.

security

One appointment per slot

A slot can be assigned to only one appointment.

lock

Available only

Booked, disabled, or unavailable slots cannot be requested.

verified_user

Re-check before saving

Only the first valid request is saved. The other sees:

This appointment slot is no longer available. Please select another slot.
07 / 09
Object-Oriented Design

Built on inheritance and polymorphism.

Role-specific behavior is modeled around a shared user abstraction.

Class hierarchy

User
Patient ClinicStaff
get_user_role() → "Patient" | "Clinic Staff"

The system calls user.get_user_role() after login. The object decides the answer, so the matching dashboard opens.

Core classes

  • User — parent with private, hashed password
  • AppointmentSlot — date, time, slot status
  • Appointment — links one patient to one slot
  • Status changes only through methods that reject invalid moves

Patterns in use

Factory · dashboards, notifications Adapter · password hashing, email Strategy · validation Generator · reports
